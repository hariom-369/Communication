# Database architecture

Status: PROPOSED · Decisions: ADR-003, 010, 028, 029

## 1. Stores and what they hold

| Store | Holds | Never holds |
|---|---|---|
| PostgreSQL 17 | Accounts, sessions (hashed), devices, public keys, conversation metadata, **E2EE ciphertext mailbox (≤30 days)**, channel posts, moderation, billing, audit | Private keys, message plaintext, backup plaintext, password plaintext, raw session tokens |
| Valkey | Presence, typing, rate-limit buckets, session cache, connection routing, pub/sub, short-lived challenges (WebAuthn, OTP attempts) | Anything that must survive loss (Valkey is treated as disposable) |
| S3 | Encrypted media blobs, encrypted backups, data exports (encrypted, short-lived), public media | Unencrypted private media |
| OpenSearch (later) | Public content indexes | Anything from E2EE conversations |

## 2. Conventions

- Primary keys: `uuid` (UUIDv7) generated by application (`id uuid primary key`).
- All timestamps `timestamptz`, UTC. Clock sync to NIC/NPL-traceable NTP (CERT-In).
- Soft delete only where legally/functionally required; otherwise hard delete + audit event.
- Every table has `created_at`; mutable tables have `updated_at` and optimistic `version int`.
- Monetary values `bigint` minor units + `currency char(3)`.
- Enum-like columns use `text` + `CHECK` constraint (easier migrations than PG enums).
- Personal data columns are tagged in a data catalogue (`db/catalogue.yaml`) with
  category, purpose, retention — drives exports, deletion and DPDP notices.
- Row-level security is **not** relied on for authorization (enforced in the service
  layer, tested); RLS may be added as defence-in-depth for multi-tenant business data later.

### Conversations & E2EE mailbox
```sql
conversations(id, kind CHECK(direct|group), mls_group_id bytea unique, epoch bigint,
              last_seq bigint, last_activity_at timestamptz, ciphersuite int, created_at,
              disappearing_seconds int null /*mirror of E2EE setting, used only for server-side expiry*/)
conversation_members(conversation_id, user_id, role CHECK(owner|admin|member),
                     joined_at, left_at, PRIMARY KEY(conversation_id, user_id))
  INDEX (user_id) WHERE left_at IS NULL
conversation_devices(conversation_id, device_id, leaf_index int, added_epoch bigint,
                     removed_epoch bigint null, PRIMARY KEY(conversation_id, device_id))
mailbox_messages(conversation_id, seq bigint, id uuid, sender_device_id, kind CHECK(app|commit|proposal|welcome),
                 epoch bigint, ciphertext bytea, size int, client_msg_id uuid,
                 created_at, expires_at,
                 PRIMARY KEY (conversation_id, seq))
  PARTITION BY HASH (conversation_id) -- 64 partitions initially
  UNIQUE (sender_device_id, client_msg_id)        -- idempotency (enforced via per-partition unique incl. conversation_id)
  INDEX (expires_at)                              -- retention sweeper
welcomes(id, device_id, conversation_id, ciphertext, created_at, consumed_at)  -- per-device Welcome
device_cursors(device_id, conversation_id, acked_seq bigint, updated_at,
               PRIMARY KEY(device_id, conversation_id))
direct_pairs(user_low uuid, user_high uuid, conversation_id, PRIMARY KEY(user_low,user_high)) -- one direct chat per pair
```

Notes:
- `seq` is assigned with `UPDATE conversations SET last_seq = last_seq + 1 ... RETURNING`
  inside the insert transaction. This serialises writes **per conversation** (not globally);
  hot conversations are bounded by group size cap. Stage-3 plan: move sequencing to the
  extracted mailbox service ([scaling.md](scaling.md)).
- Commit acceptance is `UPDATE conversations SET epoch = epoch + 1 WHERE id = $1 AND epoch = $2`
  (compare-and-set; 0 rows → `409 EPOCH_CONFLICT`).
- Deletion of mailbox rows: when `min(acked_seq)` over current devices ≥ seq, or `expires_at`
  passes (30 days, or earlier for disappearing messages). Sweeper deletes by partition in
  small batches to avoid lock storms.

## 4. Indexing plan (designed before data exists)

| Query | Index |
|---|---|
| Device fetches new messages for a conversation | PK `(conversation_id, seq)` range scan |
| List my conversations ordered by activity | `conversation_members(user_id) WHERE left_at IS NULL` + `conversations.last_activity_at` (denormalised) |
| Claim a KeyPackage | partial index `(device_id, ciphersuite) WHERE claimed_at IS NULL`, `FOR UPDATE SKIP LOCKED` |
| Active sessions for user | partial index `(user_id) WHERE revoked_at IS NULL` |
| Channel feed | `(channel_id, publish_at DESC) WHERE status='published'` |
| Username search | `users.username` unique citext + `gin (username gin_trgm_ops)` for prefix/fuzzy on public profiles |
| Retention sweep | `mailbox_messages(expires_at)` per partition |
| Moderator queue | `cases(status, priority, sla_due_at)` |

## 5. Pagination

Cursor-based everywhere; **no OFFSET** on anything that can grow. Cursor = base64url of
`{k: <sort key tuple>, v: 1}` + HMAC (prevents tampering/enumeration), e.g. message history
`(conversation_id, seq)`, channel feed `(publish_at, id)`. Page size capped at 100.

## 6. Transactions and consistency

- Submitting a message: one transaction (sequence bump + insert + outbox row).
  Isolation `READ COMMITTED` with row lock on `conversations` row.
- Commits: CAS on epoch (above) + insert commit message + membership table updates in one tx.
- Billing webhooks: idempotent on `provider_event_id`; state transitions validated.
- Cross-module workflows (e.g., account deletion) are sagas over the outbox with
  idempotent steps and a persisted state machine.

## 7. Migrations

- Forward-only numbered SQL files in `services/api/migrations/`, applied by a migration
  job before rollout (Kubernetes Job, single-run lock via `pg_advisory_lock`).
- **Expand → migrate → contract** pattern: never drop/rename a column used by the running
  version; `CREATE INDEX CONCURRENTLY`; backfills in batches.
- CI: migrate an empty DB, migrate a production-shaped snapshot fixture, and run
  `migration-lint` (e.g. squawk) to block locking operations.

## 8. Connection management

PgBouncer in transaction mode; app pool per pod sized `(cores × 2)`; statement timeout
5 s (API), 60 s (jobs); `idle_in_transaction_session_timeout` 10 s. Read replicas for
analytics/admin reads only (replication lag makes them unsuitable for message fetch).

## 9. Data retention (initial proposal — legal review L-08)

| Data | Retention |
|---|---|
| E2EE mailbox ciphertext | until all devices ack, max 30 days |
| Session records | 90 days after expiry/revocation |
| Security/login events, ICT logs | 180 days minimum, in India (CERT-In); 1 year where DPDP Rules require |
| Audit log (admin actions) | 3 years |
| Reports / cases / evidence | 1 year after case closure unless legal hold |
| Deleted accounts | 30-day grace (restorable) → hard delete; minimal tombstone (hash of username to prevent immediate re-squatting, legal-hold records) |
| Channel posts | until deleted by owner/moderation |
| Billing records | as required by tax law (L-11; typically 8 years under Indian GST/Companies Act — to confirm) |
